## 僅保留的阻擋

### B1【阻擋：可能先做了使用者未要求的改狀態動作】自動標 stateful 不能取代首次執行前的授權

引用：原則 8（21 行）、§4（119–127 行）、§6.3（196–197 行）、§7.4（257–264 行）、§7.5（271–272 行）；DECISIONS「使用者明確要求才做」。

§6.3 遇到改狀態詞就自動加 `stateful: true`，只要求 Claude 在「建立確認」時告訴使用者；但既有建立流程是**先 dry_run，再確認結果**。gate 只檢查此旗標，會在結果確認前已執行收藏、加入購物車、預約等動作。

具體反例：使用者只要求建立商品查詢流程，在示範途中順手收藏一筆；轉換器自動加旗標，Claude 為取得存檔證據就重播。真人示範中做過，不等於明確要求 Kav 自動執行；事後告知也不符合新決策。

**最小修正**：把「改狀態動作已被使用者明確要求」設為第一次 dry_run／run 派發該動作前的前置條件。既有明確要求可直接沿用，無須重問；沒有就先確認該動作。轉換器的旗標只能是候選／警告，不能自行賦予授權。skill／工具執行路徑要明確承接這個前置條件，不必新增複雜的批准系統。

此外，§7.4 的示範試跑及第二組試跑都是真實執行，**不因叫 dry_run 就沒有副作用**。對 stateful 流程要定義驗收用的安全初始狀態或經使用者同意的執行次數；不能把「加入一次」當成同意示範後再加兩次。若現階段做不到，可先拒絕自動反覆試跑 stateful 錄製草稿，其他流程照常交付。

驗收：未有明確要求但草稿含 `stateful: true` 時，輸入派發次數必須為 0；已有明確要求則不重複詢問，且只執行授權範圍內的次數。

### B2【阻擋：可能重複執行已完成的改狀態動作】form_submit 無條件保留重試，違反最新 stateful 決策

引用：§4（129 行）、WP0c（285 行）；`kfw/recipes.py:260–268`、`:321–328`；最新 DECISIONS「含 stateful 步驟的流程中途失敗不自動整段重跑」。

v3 只禁止 steps 整段重跑，卻仍寫 form_submit 維持既有重試。WP0c 又把新的 gate 接到 form_submit 的 pre／submit；設計沒有明定此類型是否允許 stateful。這必須有唯一答案，否則實作者為支援三級動作加上旗標後，很容易保留原重試迴圈。

具體反例：stateful pre「收藏」第一次已成功，後面的查詢 submit 沒效果。現有 `run_form_submit` 第二趟會再跑整份 pre；若收藏是 toggle，就取消剛才的收藏；若是加入購物車，可能再加一份。gate 每次看到合法旗標都會允許，無法防止重複。

**最小修正，二選一即可**：

- A 版 form_submit 明確拒絕任何 stateful 動作／旗標，這類草稿必須走不重跑的 steps。
- 支援 form_submit stateful，但任何 pre／submit 含此旗標時都停用整段重試；失敗回 needs_help，保留已執行動作紀錄。

這不要求改掉既有只讀 form_submit 的重試，只需遵守使用者最新決策對 stateful 的例外。

驗收：stateful pre 成功後令 submit 無效果，stateful 動作派發次數仍為 1；或在採第一種方案時，在任何動作前拒絕整份流程。

### B3【阻擋：漏錄可取得錯誤的示範一致證據】相同結果不代表漏掉的操作已被重播

引用：原則 6（18–19 行）、§2.3（70–77 行）、§7.2（239、243 行）、§7.4（257–264 行）；關聯 V03、V06。

承認偵測盡力而為可以接受，但「漏一步 → 結果必不一致」不是有效保證。Kav 示範與試跑沿用同一專屬 profile／登入帳號；示範可能已改掉 localStorage、cookie 或伺服器狀態。試跑直接讀到該狀態，就會得到同樣結果，而不需執行遺漏的操作。

具體反例：使用者在未被偵測的 iframe／closed 元件裡將項目加入收藏，然後標記主頁的「已收藏」。日誌若只有導覽＋mark，會轉成 detail_extract；重播只是重開同一頁，因收藏狀態仍在，`text-contains-v1` 通過。沒有 params 時也不需第二組測試，所有存檔條件皆可成立，但存下的流程根本不會加入收藏。非空表格比較也會有相同問題，例如漏錄選地區的操作，網站記住該地區後直接顯示同一張表。

**最小修正**：區分「成功記完已觀察到的資料」與「已驗證重播所需操作」。示範一致只證明某個起始狀態下結果相同，不能用來解除未觀察操作的風險。對可能依賴示範殘留狀態的任務，須在**明確、可重建的任務起始狀態**下試跑，或驗證必要的操作前後轉移；不能安全建立該條件就拒絕把它存為可重播流程。登入狀態可以保留，不要求清空整個使用者 profile，也不要求任意網站狀態都能自動復原。

若先縮限 A 版，可只接收已觀察到且可直接重建查詢輸入的支援表單／讀頁任務；涉及未能辨識的操作或 stateful 示範，先 unsupported。文字比較器可留作文字讀取證據，但不能把已存在的「已收藏／完成」當成動作執行證據。

驗收：做一個「示範把狀態寫入 storage／伺服器、重播不做動作也顯示相同結果」的負例。缺操作的草稿必須不能以該結果取得可存的重播證據。對純讀取且本來就不需該操作的任務，則無須為無關點擊拒絕存檔。

## 實作注意事項：不另阻擋本版

以下都可以在對應 WP 實作與測試時處理；不是要求再開新一輪設計功能。

| 編號 | 範圍 | 注意與驗收 |
|---|---|---|
| I1 | §2.2／V10 | 不把裸 `executionContextId` 當跨程序永久 ID；使用本地 epoch 與 context 身分對照，舊 context 的遲到資料不得掛到新文件。CDP 官方明說 contextId 可能跨程序重用，提供 uniqueContextId 避免誤 evaluate。[CDP Runtime 定義](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/js_protocol.json) 屏障測試覆蓋離頁前舊文件的最後一組，而不只目前文件；舊文件缺收束證據時沿用 incomplete 原則。arm 前的輸入須緩衝或記缺口，不可默默丟掉；BFCache 返回已停止錄製的頁面不得恢復收集。 |
| I2 | §3.2、§7.2／V04、V05 | 提交前先提交待定欄位組，避免最後一個字或 blur 正規化落在舊快照之外。空值若代表使用者刻意清空，不能因 fields 只收非空而消失；不能表達就 unsupported。無 label／重名／checkbox 的拒絕不能實作成單純從 fields 過濾。相依欄位至少覆蓋自動清空及延遲重設的負例。 |

WP-S、WP0a、WP0b 可照既定方向開工。WP0c 可做已知禁止規則與未派發輸入的測試；新增 stateful 放行前先補 B1、B2。B3 是錄製流程標為可重播並存檔前的必要邊界，不需因此暫停獨立的 CDP／觀察工作。
