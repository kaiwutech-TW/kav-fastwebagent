# 寫配方的共同規則

這些規則都是實測踩過坑才定下來的,出處寫在 `.flightwake/TRAPS.md`。

## 格式

```json
{
  "name": "thsr-timetable",              // 小寫英數字和 -,3–60 字
  "type": "form_submit",                 // form_submit | search_compare | detail_extract | steps
  "description": "一句話:做什麼、回傳什麼",
  "domains": ["thsrc.com.tw", "高鐵"],     // find_recipe 用來比對:網域、常見叫法
  "intents": ["時刻", "車次"],             // find_recipe 用來比對:使用者常用的動詞或名詞
  "params": {
    "date": {"description": "出發日期", "example": "2026/10/05", "pattern": "\\d{4}/\\d{2}/\\d{2}"}
  },
  ...各類型自己的欄位
}
```

- 在任何字串裡寫 `{參數名}`,執行時會代入參數值。
- **每個參數都要有 `example`;格式固定的一定要寫 `pattern`**(regex,整串比對)。
  參數格式錯是最常見的失敗原因:高鐵的日期寫成 `2026/10/5`,結果查到別的日子。
- 列舉型的參數(站名、分類)可以把所有值寫進 pattern,例如 `"南港|台北|板橋"`,錯字會直接被擋下。

## 原則

1. **能用程式判斷的就不要交給模型。** 型號、容量、日期、數字比對都交給程式(must / must_not、pattern、expect_text)。
   Kev 只處理語意問題(是不是配件、是不是組合包、哪個選項代表「台北」)。
   實測:型號比對交給 Kev,Switch Lite 會被當成 Switch 2。
2. **完成要由程式證明。** 每份配方都要有機器檢查得了的完成條件(結果列數量、頁面上必須出現的文字)。
   實測:模型說「完成了」的時候,結果其實還沒載入。
   - **列表的 `rows.pattern` 只鎖「每列一定有、別處沒有」的錨**(例:`元/月`),不要描述格式細節(整數坪數、`\dF/\dF`)。
     實測:591 列表 30 張卡片,格式細節的 pattern 只中 26 張(3.5 坪、頂樓加蓋、B1 都不中),漏掉的一張正是答案。
     結果裡的 `rows_skipped` 是「同一個列表裡不符 pattern 的列數」,**大於 0 就要放寬 pattern 再跑**,不能當作完成。
3. **label 照抄 `inspect_page` 的文字。** 不要自己翻譯或縮寫。對不到欄位時,Kav 會回報 ambiguous 或 no,不會亂猜。
4. **一個配方只做一件事。** 「查時刻再訂票」要拆開;訂票本身不做。
5. **規格要在看到結果之前寫好。** 不要根據某一次試跑的結果去調 must / must_not 或門檻,那樣只是剛好在那一次通過而已。
6. **試跑通過之後要看截圖。** `passed` 只代表你寫的條件成立;條件本身寫錯的話,錯的結果也會通過。
