# kav-fastweb:用配方跑網站任務

分工:**你(Claude)負責規劃和寫配方,Kav 負責執行和驗證。** 配方是 JSON 資料,不是程式碼。
Kav 用本機 Chrome、程式判斷載入和完成,Kev 只回答模糊的判斷題。每次執行都會附上證據(截圖路徑)。

## 0. 跟使用者講話的方式(使用者不是工程師)

- 對使用者一律說「**流程**」,不說配方、recipe、dry_run、pattern、JSON、selector。使用者只需要判斷「結果對不對」。
- 用使用者的語言回覆。
- **建立新流程**(使用者說「幫我做一個流程…」,或要做的事還沒有配方):
  1. 只在缺資訊時問,而且一次問完:哪個網站(網址)?每次會換的是哪些(例:日期、站名)?想看到什麼結果?能從需求推斷的就不要問。
  2. 照第 3 節寫配方、試跑,自己先看過截圖。
  3. **存檔前給使用者確認一次**:列出這次的結果(重點欄位)和截圖路徑,問「這是你要的結果嗎?」。
     使用者說對 → 存檔,然後告訴他「以後直接說『<一句範例說法>』就能用」。說不對 → 照他說的改,再試跑、再確認。
  4. 只有**建立**時問;之後使用流程、修壞掉的流程都不用問(修好再回報,見第 4 節)。
- **「我有哪些流程?」** → `list_recipes`,每個流程用一行白話說明做什麼,加一句範例說法(從 `example_params` 組)。內建的標「內建」。
- **「刪掉 X 流程」** → 確認是哪一個後 `delete_recipe`;告訴使用者檔案移到回收區、可以救回。內建流程不能刪。
- **「結果不對 / 少了某欄」** → 當成修正:照第 4 節「修配方」改好、重跑、再回報。
- **「我示範給你看」/「我做一次給你看」** → 照 `references/recording.md` 開始錄製。你寫不出流程(試跑同一問題兩次不過)或修不好(同一處兩次不過)時,也可以**先問**使用者要不要示範一次;對方同意才開錄。

## 1. 先找配方(最便宜的路線,大多數情況到這裡就結束)

1. `find_recipe(使用者的需求或網址)`
2. 有 `status: verified` 且符合需求的配方 → 照它的 `params` 說明整理參數 → `run_recipe(name, params)`
   - 參數格式有強制檢查(例如日期 `2026/10/05`,不能寫 `2026/10/5`)。被拒絕時照錯誤訊息修正,不要猜。
3. 回報結果時附上重點數字和證據路徑。`status` 不是 `done` 就照第 4 節處理。

## 2. 沒有配方:判斷任務類型,只讀對應的那一份

| 使用者想做的事 | 類型 | 讀這份 |
|---|---|---|
| 在一或多個網站**搜尋**,從結果**列表**挑出符合的(比價、找職缺、找房) | `search_compare` | `references/search-compare.md` |
| **填表單送出**,讀結果(時刻表、包裹追蹤、查詢系統) | `form_submit` | `references/form-submit.md` |
| 讀**一個已知網址**的內容(商品頁價格/庫存、公告頁) | `detail_extract` | `references/detail-extract.md` |
| 替使用者登入、解驗證碼、付款、下單、送出個資 | **不做** | 直接告訴使用者原因(使用者自己在 Kav 專用 Chrome 登入過的網站可以用) |
| 要點**好幾頁**才到結果、中間要**從列表挑一筆**、或要**翻頁**收集 | `steps` | `references/steps.md` |
| 條件分支很多、每次路徑都不同 | 不用這個 skill,改用 Claude in Chrome |

所有類型都要遵守 `references/recipe-rules.md`(寫配方的共同規則,**第一次寫配方一定要讀**)。

## 3. 寫配方的流程

1. `inspect_page(url)`:看欄位名稱、選項、按鈕文字、列表、結構化資料。**配方裡的 label 必須照抄這裡出現的文字**。
2. 依類型的參考檔寫出配方 JSON。
3. `dry_run(recipe, 範例參數)`:
   - `passed: false` → 看 `reason` / `hint` / `steps` 修正後再試。同一個問題試兩次還不過,就停下來告訴使用者卡在哪,並問要不要示範一次給你看(`references/recording.md`)。
   - `passed: true` → **打開證據截圖確認結果真的對**(這一步不能省:程式條件寫錯時也可能通過)。
4. 新流程:先照第 0 節給使用者確認結果,使用者說對了才存。`save_recipe(recipe, dry_run_id)` 只接受「這份配方本身」剛試跑通過的紀錄。改過配方就要重新試跑。
5. 用 `run_recipe` 完成使用者原本的需求。

## 4. 處理 needs_help

| reason | 做法 |
|---|---|
| `login_required` / `verification` | 請使用者在 Kav 專用 Chrome 視窗手動處理,完成後重跑。**不要嘗試繞過** |
| `access_denied` | 請使用者關閉 Cloudflare WARP / VPN / 私密轉送 |
| `field_not_found` / `submit_not_found` | 配方跟頁面對不上:**直接修**(見下方「修配方」) |
| `field_not_set` / `result_not_proven` | 看 `steps` 和截圖;參數格式不對就改參數。截圖裡結果其實在頁面上、只是程式沒抓到 → 配方的完成條件對不上,**直接修** |
| `no_match` / `suspicious_prices` | 比價類:檢查 must / must_not,讀 `suspicious` 那幾筆再決定要不要告訴使用者 |
| `kev_not_running` | 請使用者照 README 啟動 Kev |
| `unsafe_action` / `stateful_not_authorized` | 程式拒絕了付款、登入、改狀態這類動作。**不要**為了讓它通過而加 `stateful` 或 `allow_stateful`;告訴使用者被擋的是哪個動作。改狀態的動作只有使用者明確要求時才做(見 `references/steps.md`) |
| `bad_request` 且提到 `unsupported field(s)` | 流程用了這個引擎不認得的欄位:是你打錯就改;是新功能就請使用者重開 Claude Code(引擎在啟動時載入)。**不要刪掉那個檢查來讓它跑過** |

**修配方(不用先問使用者,修好再回報)**
1. 讀現有配方:使用者版在 `~/.kav-fastweb/recipes/<name>.json`(優先),內建版在 repo 的 `recipes/`。不用另外搜尋檔案系統。
2. `inspect_page` 或用寬鬆條件 `dry_run`,看頁面真實的文字/欄位,只改對不上的那一處。
3. **取代**舊條件,不要把舊的留成備選(它已經證明對不上,留著只會誤中別的東西);也不要放寬到什麼都會過。
4. `dry_run` → 看截圖逐項核對 → `save_recipe` → `run_recipe` 完成使用者原本的需求。同一處修兩次還不過,才停下來告訴使用者,並問要不要示範一次(錄完用 `compare_to` 比對)。
5. 回報:先給答案,再用一兩句說「配方哪裡跟頁面對不上、改了什麼」。**不要斷言「網站改版了」**:你分辨不出是網站變了還是配方本來就錯,只說對不上的事實。

## 5. 不要做的事

- 不要用跟使用者不同的語言回覆(使用者用中文問就用中文答)。

- 不要把使用者的帳密、個資寫進配方或參數。
- 不要為了讓試跑通過而放寬完成條件(例如把 `min_rows` 改成 0)。
- 不要大量、高頻地執行(這是給使用者發起的任務用的,不是大規模爬蟲)。
